# 民非限定性维度：Contracts v2候选规格与合成验收

本文件给主协调评审接口及持久化升级使用，**没有修改Contracts、Core、Desktop或SQLite**。正式依据复用已归档财会〔2024〕25号及财会〔2025〕6号；数据版本 `2026.10.25.2`，不是生产认证。

## 为什么v1字段不足

现有 `VoucherLine(AccountCode, Summary, Debit, Credit)`不能区分同一个4101或5301下的限定与非限定，也不能关联不同捐赠协议。仅新增“限定性”总账科目或按科目总余额结零，会掩盖从A协议挪到B协议、或从限定改为非限定的错结转。需要稳定分录行ID、分类、限制证据版本和业务动作类型；不能把这些事实压入摘要字符串。

| 事实 | 正式依据 | 规格约束 |
|---|---|---|
| 限制来自外部提供者或法律、行政法规，内部预算本身不够 | 第67条，PDF28页 | 限定行必须绑定具体外部限制证据；董事会预算可作管理标签，不能替代 |
| 受限资产相关支出计限定性费用 | 第68、78条，PDF28、35页 | 费用功能科目与限定类别分别保存，不能全部费用结到3101 |
| 收入、费用分别按两类结转净资产 | 第74—75、78—79条，PDF33、35页 | 结转保留类别及限制ID/版本；两个净资产分量分别可解释，损益各明细结零 |
| 共同费用按合理方法在活动间分配 | 第77条，PDF34—35页 | 留分配依据、审批、输入量、尾差政策和凭证行桥接；不把某个比例写成法定比例 |
| 完全解除、撤销等才形成相应重分类 | 第69—70条，PDF29页；3101/3102说明103—106页 | 时间到期但用途仍受限，不自动转；支出本身不触发旧法使用重分类 |
| 可靠凭据的服务捐赠可同时确认收入与费用 | 第18条第（四）项，PDF7页；4101说明108页 | 需要确认判断证据；非现金收入费用不能制造现金流 |

5601仍为专门复核项：PDF124—125页特定账务说明与146页一般费用双分类列报表述均保留。本规格不自行裁定其限定性自动处理。迁移旧费用余额必须为零的要求仍沿v1执行，不由新增维度绕开。

## 建议的类型边界

以下是候选形状，须由主协调确定最终类型、兼容及schema升级；不是已冻结或已实现的共享接口。

```csharp
enum RestrictionClassV2 { Unrestricted, Restricted }
enum RestrictionSourceKindV2 { ExternalProvider, LawOrAdministrativeRegulation }
enum EvidenceDecisionV2 { Unknown, Satisfied, NotSatisfied }
enum NonprofitOperationV2 { OrdinaryActivity, Closing, RestrictionRelease,
    RestrictionIncrease, RegisteredCapital, PriorYearAdjustment }

record VoucherLineV2(Guid Id, string AccountCode, string Summary,
    decimal Debit, decimal Credit, RestrictionClassV2? RestrictionClass,
    Guid? RestrictionId, int? RestrictionVersion, Guid? AllocationLineId);

record RestrictionEvidenceV2(Guid Id, int Version, RestrictionSourceKindV2 SourceKind,
    string EvidenceReference, string Terms, DateOnly? TimeConditionEndsOn,
    string? PurposeCondition, string EvidenceSha256);

record ReleaseAssessmentV2(Guid Id, Guid RestrictionId, int RestrictionVersion,
    EvidenceDecisionV2 TimeDecision, EvidenceDecisionV2 PurposeDecision,
    bool ProviderRevoked, string ScopeEvidenceReference, string Reviewer);
```

还需独立、不可变地保存：规则包ID/版本/hash绑定；分配底稿ID、共同费用原金额、受益活动、客观输入量、选择方法、复核人、尾差政策及到分录行的对应；制单、审核、已记账状态；重分类金额和解除范围；证据版本及事件日期。金额沿用decimal与整数分存储，不改成double。

资产/负债行不冒充“收入费用限定类别”。如要追踪受限银行余额，应另设资金来源/项目子账或等价可追溯关联，不能只给所有银行行一个限定标记就声称已完成资金控制。3101/3102由科目本身确定类别；受限净资产仍须能追到具体限制记录，不能只看3102合计。

限制记录可以包含时间、用途或两者；`Unknown`不得当成已解除。一个捐赠协议可能含多个条件或可独立解除的部分，须通过有据的范围/分项记录表达。本验算器的每个restrictionId代表**一个完整解除范围**；如果A300全部解除、B700仍受限，应分别记录，不能把同一A1000写“条件全部满足”后只转300。真实部分解除、多层条件及其他法定重分类另建场景验收。

## 验证不变量

1. 普通收入和费用行都必须明确类别。限定行证据存在、文本非空、属于外部或法律来源且有具体条件；非限定行不得带外部限制ID。不能用空字符串、内部预算或默认枚举掩盖未判定状态。
2. 用 `(accountCode, restrictionClass, restrictionId, restrictionVersion)`核对明细。科目总额结零不意味着各类各协议结零。结转净资产的类别、协议与被结转损益相同，且金额不能超过其明细余额。
3. “业务活动成本/管理费用”等功能分类与限定类别相互独立。分配总额守恒，每个凭证行只被分配一次，底稿与凭证金额、类别、限制ID一致。分配依据合理性是人工判断，算法只能验证已声明的方法。
4. 重分类是有证据的独立动作。不能改称普通Activity、Closing或补一笔Opening绕过。解除评估与分录关联同一限制，且逐限制核对可释放余额，防止借用B余额或同一A重复释放。
5. 本例的完整解除转出该限制记录的全部相关净额。此前损益应按分类结转，或在正式工作流中有可复核的期内明细衔接；不以全组织3102余额代替该限制净额。
6. 期初取自冻结并经复核的快照，保存来源hash、账套及期间、审核人；不能在已有活动后用“期初”改分类。合成验算仅允许第一笔至多一个Opening，要求含资产/负债，旧收入费用不带入。它不替代真实导入授权及迁移底稿。
7. 已记账数据沿用不可逆要求。新增分类/限制版本不能修改已记账历史；变更通过适用制度允许的更正/调整事件，保留原证据和报表可复现性。持久化升级由对应owner另行设计、测试。
8. 报表按分类取未含结转的期间损益；以两类净资产分别核对期初＋收入－费用＋有据重分类/调整＝期末。缺失分类、比较数或证据不能静默填0。

## 固定合成算例

可机器读取文件：`scenarios/nonprofit-v2.json`。全部金额、协议和审批是假数据，预期数字先手算写入，再由 `nonprofit_scenarios.py` 验算；并非实现运行后回写预期。

| 正例 | 独立预期 |
|---|---|
| 同样捐赠1000、支出200，分别限定/非限定 | 现金均800；前者净资产R800/U0，后者R0/U800；使用支出不额外重分类 |
| 期初R1200/U800，收入R3000/U2000，共同费用1000按有据3:2分配 | 费用R600/U400；期末R3600/U2400，资产6000；本期现金净增4000；各损益明细结零 |
| 101分共同费用按1:1:1合理分配 | 按本例选定最大余数法及稳定行ID，34/34/33分，总额101；不是制度规定的唯一方法 |
| A300全部解除、B700仍受限 | 资产1000不变，U300/R700；收入和现金变动均0；重分类两类分别+300/−300 |
| 可靠凭据非现金服务捐赠1000 | 收入1000、费用1000；现金及净资产变动0；不能把净额0误当没有业务活动 |

21个拒绝例覆盖：缺分类、缺协议、内部预算、错结转净资产、换类别/协议结转、时间到期但用途未满足、旧法使用自动重分、尾差丢失、底稿到凭证金额不一致、5601自动处理、未审分配依据、隐藏重分类、解除协议不匹配、空条件、跨协议超额/重复/范围不明解除、Opening伪装、2025交易套新表。额外单元变异验证空证据、Closing夹带解除评估、重复分配同一凭证行等。

运行 `python3 rules/validate.py` 会同时执行27例（6接受、21拒绝）；`test_rules_v2.py`另核关键手算数及故意变异，整体53项单元测试通过。验算全部使用整数分，且不受外部Decimal上下文精度影响。

## 明确未覆盖

验算器是有限验收oracle，不是 `ILedgerService`，不会保存、审核或过账任何凭证。只演示正金额损益的简单期末结转、受限转非受限的完整解除，以及两类分配。负收入/退款、捐赠附条件确认、注册资金、增设限制、复杂多协议/分期条件、负净资产、5601、重大前期差错/3201、税务、完整报表/现金流分类、完整迁移及生产账套并发事务均未完成。

服务捐赠确认前提、捐赠计量、限制事实、解除事实和分配合理性在样例中是明确的人工作业假设，不能因为机器算术通过便自动判定真实业务满足条件。主协调扩Contracts后，还需由Core与SQLite owner分别实现和测试，再以同一预期样例做跨层验证；本包的53项测试及27例不等于三类业务会计逻辑全验。
