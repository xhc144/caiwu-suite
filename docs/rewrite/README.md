# 重做计划：怎么用这两份提示词

| 文件 | 给谁 |
|---|---|
| [wave0-task.md](wave0-task.md) | 原样贴进 **1 个** Codex 云任务（地基） |
| [orchestrator-prompt.md](orchestrator-prompt.md) | 原样贴给 **GPT 总控**，由它输出后续几十个 Codex 任务的提示词 |

## 之前为什么跑偏

1. **没有共同地基就开始并行**：每个对话各自发明一套数据模型和目录结构，最后合不到一起。
2. **WPF 在 Codex 云端跑不起来**：云端是 Linux，GPT 没法真正运行和测试界面，于是大量精力花在 Windows CI、截图证据、交付门禁、SHA 清单上（看看 `.ai-handoff/STATE.md` 就知道）。
3. **任务写得太虚**：只写"参考文档实现"，没有落到原版的具体窗口和规则上。

新方案对应解决这三点：
1. 先用 1 个任务把地基做好，后面的任务各自只改自己的目录。
2. 改用 TypeScript 技术栈，在 Linux 上能完整跑起来、能测试。
3. 每个任务都列出原版的窗口名和规则清单，并且禁止写证据文档。

## 分几波

| 波次 | 任务数 | 内容 |
|---|--:|---|
| Wave 0 | 1 | 地基：目录、核心数据模型、模块自动注册机制、通用组件、测试夹具、AGENTS.md、CI |
| Wave 1 | 21 | 各业务模块同时开发：账套、基础档案、期初、凭证录入、凭证管理、结账、账簿、余额表、报表引擎、分析、出纳、发票、工资、资产、进销存、系统管理、备份、打印、工作台、桌面壳、制度模板 |
| Wave 2 | 约 22 | 逐模块对照原版补漏，加上成本核算、三套法定报表 |
| Wave 3 | 约 10 | 全年流程测试、跨模块联调、性能测试、Windows 实机问题修复 |

## 操作步骤

1. **补充难用点**：打开 `orchestrator-prompt.md`，在「要改掉的难用点」第 15 条写上你自己想改的。
2. **开地基任务**：把 `wave0-task.md` 全文贴进一个 Codex 云任务，基于 main 分支，attempts 选 4。几个版本里挑一个：CI 是绿的、`pnpm check` 通过、PR 描述里「未实现」最少。为它建 PR，合并到 main。
3. **配置 Codex 环境**：按 `app/CODEX_SETUP.md`（地基任务会生成这个文件）设置 Codex 环境的 setup script。不设的话，后面的任务装不了依赖，也跑不了 E2E。
4. **交给总控**：把 `orchestrator-prompt.md` 全文贴给 GPT 总控，它会输出 21 个任务的提示词。**一定要等 Wave 0 合并之后再开这些任务**，因为 Codex 任务从开任务那一刻的 main 起步。
5. **同时开 21 个任务**：attempts 按总控给的建议开，2 到 4 个。
6. **合并**：每个任务做完就建 PR。CI 是绿的，并且只改了它自己的目录，就直接合并，先后顺序无所谓。遇到锁文件冲突，或者 PR 改了别的目录，就把 PR 贴给总控处理。
7. **进入 Wave 2**：全部合并后，告诉总控"Wave 1 全部合并"，它会输出 Wave 2 的任务。
8. **实机试用**：M21 合并后，GitHub Actions 会生成 Windows 安装包。自己装上试用，把发现的问题贴给总控，这些问题进入 Wave 3。

## 额度怎么花最值

- **attempts**：同一个任务跑多个版本再挑最好的。最烧额度，也最能提高质量。凭证录入、报表引擎这类大任务开 4 个。
- **Wave 2 逐模块补漏**：每个模块一个任务，对照原版逐个窗口、逐条规则核对。可以并行很多路，而且每一路做的都是实打实的功能。

## 如果想继续用 C#

把 `wave0-task.md` 里的技术栈一节换成 .NET + Avalonia（Avalonia 能在 Linux 上做无头界面测试），其它规则不用改。但 Codex 写 TypeScript 和 React 明显更稳，不建议换。
