# 原账套与版本兼容路线核查

核查日期：2026-10-25。仓库：`xhc144/caiwu-suite`；只读证据基线：`3b0c59b02d8941c32ac176309555c03c94bb4213`。本文只核实原账套、数据结构与升级条件，不实现业务或迁移工具。

## 结论与目标约束

目标是原软件的升级版：保留原功能、账套、菜单/窗口/按钮相对布局、快捷键及操作习惯，现代化视觉并改善经确认难用的局部。原账套兼容是验收前提；旧 `0.1.0.4` WPF 预览和其自建 `.caiwu` SQLite 格式不能充当目标基线。

**现有证据支持继续研究沿用原 SQL Anywhere 数据及在副本上验证兼容；尚不支持宣布能够直接打开、写回或原地升级用户原账套。** 保守顺序是：识别原安装与数据组成 → 封存完整备份 → 在第二份副本上只读核验数据库目录与 schema → 验证同格式读取 → 最后才讨论经过授权的副本写入/迁移。不能先迁入删减字段的 SQLite，再称为原软件升级。

| 路线 | 本轮判定 | 边界 |
|---|---|---|
| 依据已有静态分析保留原功能与界面结构 | 可继续设计 | 分析已经完成并入库；静态描述不等于可编译 PB 工程或实际兼容测试 |

| 原账套原地写入或原地 schema 升级 | 当前不放行 | 没有可回滚、逐版本迁移及原程序复开证据；备份存在也不能替代兼容验收 |
| 复制到新目录，保留 SQL Anywhere 格式后验证 | 优先验证路线，未执行 | 必须核对整个数据库、日志、报表与其他依赖；复制成功不等于可打开 |

| 原数据只导出 CSV、仅余额/科目导入、自建 `.caiwu` 继续使用 | 不能作为本目标的完成方案 | 会丢失模块状态、关系、历史流程和原格式互操作能力 |

## 原存储实际可确认到哪一步

### 数据库与文件

- 原分析指向 Sybase SQL Anywhere / Adaptive Server Anywhere 8/9；清单也列出 `asa8` 下的 `dbeng8.exe`、`dbodbc8.dll`、`dbodbc9.dll`、`dbserv8.dll`、`dbserv9.dll` 等。**这确认了运行时依赖线索，不能仅凭目录名或混装 DLL 确定每个 `.db` 的文件格式版本、实际运行引擎或补丁号。**
- 三套载荷都有 `rhsj\Rhzw01.db`：轻松与成本为 16,230,400 字节且 SHA256 相同；民非企为 5,687,296 字节、SHA256 不同。它们是安装载荷中的数据库，不能当作用户真实账套，也不能推断三套运行后数据完全相同。
- 三套都有 `Rhzw8.ini`、`autoupdate.ini`，对应文件哈希各不相同；启动静态流程读取 `Rhzw8.ini`。必须核实实际安装使用的配置及其数据库名/路径/启动方式，不能拿某一产品配置覆盖另外两套。
- 三套都有同哈希的 `rhsj\Bb000.vts`。其存在和恢复窗口对“报表文件”“打印格式文件”的检查，要求备份时保留相关文件；当前材料不足以断言这个 VTS 的全部内容、与账套的绑定或所有报表是否只存在于此文件。
- 清单未列出 `.log`，不证明实际库不使用事务日志；也不能假定用户目录只有上述两个文件。事务日志、镜像日志、外部 dbspace、附件及路径依赖均须从具体库/配置核实。

特别需要消除工具歧义：轻松清单的 `dbbackup.exe` 记录 128/141、`dbunload.exe` 记录 139/153、`dbvalid.exe` 记录 140/154，分别指向同一安装目标路径但大小和 SHA256 不同；轻松还同时列出 `dbeng8.exe`（131）与 `dbeng9.exe`（144）。民非/成本的清单只列出 `dbeng8.exe`，不能据它们另有 9 系列 DLL 推断实际使用 9 引擎。必须核查实际生效文件与版本；不能按文件名任选工具、按记录顺序猜最终安装结果，或把同名记录相互覆盖。上述编号均为该产品 CSV 的 `record` 值，不是 CSV 行号。

### 账套不是已证实的“一个文件一本账”

`datawindows.json` 中三产品的 `dw_tzjl_1` 查询都直接访问 `dba.xttz` 的 `dm`、`tz_name`、`sm`。套账管理窗口使用两位数字/字母代码，并排除 `ID/XL/ZC/CS` 等代码。这证明存在数据库侧套账目录和保留代码规则。

当前资料**没有闭合**账套代码 → 数据库文件 → owner/schema/表 → 出纳/发票连接的映射，不能断言每本账是独立 `.db`，也不能断言全部账套一定共用一个物理库。还需核实登录切账时是否切换数据库、用户/owner、表名或连接参数。`tables.json` 没有 `xttz` 的定义；窗口摘要中的 `dba`、`sys` 等抽取结果不能直接当作完整表名建表。

因此，保守物理备份应覆盖经核实的完整数据库依赖集合，而不是先选一个“账套文件”复制；业务层隔离一本账也不能替代物理库的整体备份。

### ACD 模板与 schema 的范围

- 每套安装包有 60 个 `aNN.acd` 记录；本轮按清单同路径哈希比较，60 个对应模板在三套间均相同。已有分析已从 180 个归档中的 `rhsj/data_stru.txt` 解析模板 DDL。ACD 是模板/归档来源，不是经证实可直接用数据库驱动打开的数据库文件。
- `aclist.txt` 对应 44 个可见制度选项；60 个归档记录不等于 60 个不同、可见、现行制度。比如企业 `a01/a02`、小企业 `a05/a52`、民非 2026 `a54`，以及停用制度，必须保留原选择与历史，不自动套用最新版替换旧账。
- “三产品对应模板相同”与“所有模板共用同一 schema”是不同结论。表文档明确记录同名表的变体：`kmbm` 7 种、`pz` 6 种、`pzdj` 3 种、`slz` 8 种、`cn_mx` 8 种、`dwk` 11 种、`xt` 4 种。220 是汇总表名数，不能承诺每本账恰有 220 张表。
- `tools/original-analysis/tables.py` 从 `template-schemas.json` 选择覆盖模板最多的定义，输出其列、`variant_count` 和该定义的 `templates`；**这里的 `templates` 不是该表所有变体的完整适用模板集合。** 当前入库 `tables.json` 没有全部变体定义、逐模板完整 schema、完整索引清单、所有约束/触发器/存储过程/授权。生成器所消费的完整 `template-schemas.json` 未见于本 checkout。不能直接把简表转换成全量重建脚本。
- `dbver` 仅在汇总中出现一个定义，覆盖 `a45/a47` 两个模板；字段为 `id integer`、`dbver numeric(18,2)`。没有其在实际库中的值、更新程序和适用范围。它不能充当所有原账套统一的升级开关，也不能与 SQL Anywhere 文件格式版本或新版程序版本混为一谈。

## 不能无损压进现有 SQLite schema 的具体内容

现有 `Caiwu.Persistence.Sqlite` 用 `Microsoft.Data.Sqlite` 打开连接，要求自有 `application_id` 和 `user_version`，其主 schema 是 `ledger/accounts/vouchers/voucher_lines/audit_events`，金额以整数分保存。它不识别 SQL Anywhere 页格式，也没有原数据库连接/迁移实现。已有构建、SQLite 集成和备份测试不能证明原账套兼容。

原表中已经可见的差异包括：

- `pz` 的主流定义含 `double` 金额、外币金额/汇率、数量/单价、项目/客供/部门/人员、现金项目、合同和到期日等；`pzdj` 另存制单/审核/记账人及日期。不能只抄日期、科目、借贷金额，再声称保留凭证。
- `pzmb_pz` 同时有 `numeric(18,2)` 与 `float`；其他表还存在不同 scale 的 numeric。不得统一乘 100、取整，或按字段标题猜类型。须记录原声明、原值精度与原程序显示/运算规则，另核 NULL、空字符串、尾随空格、日期和字符集/排序规则。
- `bbml*` 的 `bb_nr`、`pz_fj.nr`、`zc_pic.pic` 为 `long binary`，不能用 CSV 代替；备份必须逐对象核对长度/哈希并核实解释这些内容所需的原组件。
- 某些表没有在简表中标出的主键；不能自行加唯一约束、去重或重排。模板变体和原始业务关联未核清前，不删除“重复行”、不重新编号、不按合计相等掩盖明细差异。

如新版需要额外界面设置，可另行设计非业务设置存储；它不能取代原账套或制造两份相互脱节的业务真相。本轮没有新增此类存储。

## 分开验证四种“升级”

### 1. 原程序/界面改版

原主程序是 x86 PB9 二进制；原分析及导出器给出了窗口、控件、动作和 SQL 线索，当前 checkout 未提供已验证的原 PBL/PBW/PBT/资源和可重建工程。可编译性、外部 DLL/ActiveX、报表组件及合法构建/分发条件都未闭合。

若后续有合法可用的原工程，先在隔离环境复建未经改动的原版本并与原版行为对照，再讨论界面改版。若没有原工程，现代化界面接入原数据库是可研究的另一条实现路线；仍必须保留原功能/布局/流程和原账套，不能用现有简化 WPF 预览替代业务基线。二者均不能在本轮宣称已能产出可运行新版。

### 2. 原数据库原格式打开

优先目标是在精确匹配的 SQL Anywhere 运行时和驱动下，只读识别副本，核实账套目录与 owner/连接规则，不改变文件格式或应用 schema。驱动位数必须与选定宿主匹配；原 x86 组件不能直接视为已适配现有宿主。须记录每次实际加载的引擎/驱动版本、文件哈希与绝对工具路径，避免 PATH 同名工具混用。

**“只发 SELECT”不等于物理文件没有写入。** 引擎启动、恢复、连接触发逻辑或原应用登录都可能改变状态；测试必须作用于第二份副本，选择已核版本文档支持的只读方式，并在停止后复核数据库及日志的哈希。需恢复或不能只读启动时先记录原因，不能静默改成可写、重建日志或清除审计。厂商对备份验证也建议验证备份的副本，并说明恢复会修改它：[SQL Anywhere 验证工具说明](https://infocenter.sybase.com/help/topic/com.sybase.help.sqlanywhere.12.0.1/dbadmin/dbvalid.html)。这是通用机制依据，不是对本项目 8/9 文件的实测。

### 3. 应用 schema 升级/原备份引入

原界面确有 `w_tzjl_get` / `w_tzjl_get_all` 的“引入备份文件”、`cbx_update`“自动升级”，以及 `w_hf` 的“恢复数据”。它们还检查结构、报表、打印格式文件；恢复文案明确会覆盖当前套账数据，包括出纳。`w_ini_bf` 则明确只备份部分数据、仅用于初始化，不能作为全量保障。

这些入口证明原程序设计了兼容/恢复流程，**不证明任意旧版本均受支持，也不证明当前文档已包含迁移 SQL、事务边界或失败回滚算法**。自动修复、抑制错误、不重建结构等选项不能作为默认测试手段。应定向核查已有本地导出的相关事件和调用函数，补出准确版本条件、创建对象/DDL、数据变换及报表处理清单；不重新反编译全包，也不上传完整派生物。

若 schema 无需变化，界面改版应优先保持业务结构。若确需变化，先对副本生成可审阅差异与迁移方案，逐版本说明前置指纹、操作、验证、失败处置和是否可由旧程序复开；不能在用户库登录时自动改 schema。对数据库引擎或 DDL 不可逆变化，回退指恢复封存的整个旧环境/数据集合，不承诺执行反向 SQL 即可降级。

### 4. SQL Anywhere 引擎/文件格式升级

厂商将“更新服务器软件”“升级系统目录”“卸载/重建文件格式”区分处理。SQL Anywhere 12 的官方文档明确：9 或更早数据库进入该代须卸载并重建，不能直接启动旧文件：[SQL Anywhere Server upgrades](https://infocenter.sybase.com/help/topic/com.sybase.help.sqlanywhere.12.0.1/sachanges/v10upgrade-up-sql-any-123456.html)。SQL Anywhere 17 也提供针对 9 或更早数据库的重建流程：[Rebuilding a Version 9 or Earlier Database](https://help.sap.com/docs/SAP_SQL_Anywhere/a3e900ad39b94d689987e838835f39fe/815840126ce210148ac5f7983623a016.html?locale=en-US&state=PRODUCTION&version=17.0)。这些说明建立候选路线，不能据此指定当前应采用哪个目标版本或省去项目兼容测试。

未来若确需升级引擎，选取经许可且支持源文件版本/操作系统的精确工具，输出到全新目录的全新数据库，保存原文件和原日志。禁止使用会替换旧库的选项或覆盖目标；例如文档中的“创建新库”与“替换旧库”是不同选择。迁移后须比较 owner、权限、类型、字符集/排序、索引/约束/触发器/过程和业务结果；引擎重建通过不能证明 PB 客户端、报表组件、原应用与新版均可继续使用。原程序对新文件格式的复开能力必须单独验证。
